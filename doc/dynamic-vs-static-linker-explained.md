## 1. What Problem Does This Code Solve?

This project loads ELF shared objects (`.so` files built for ARM Cortex-M) into
RAM on a bare-metal microcontroller — no operating system, no `mmap`, no
userspace/kernel split. The loaded library must be able to call functions in the
main firmware image (`printf`, `sinf`, `operator new`), and functions in other
loaded libraries (`lib_a` calling into `lib_b`).

Two separate implementations live side by side:

| Directory | Runs on | Purpose |
|---|---|---|
| `src/dynamic-nolib/` | Cortex-M target (bare-metal) | Runtime `dlopen`/`dlsym`/`dlclose` |
| `src/dynamic-newlib/` | Cortex-M target (hosted newlib) | Dynamic loading with revertible GOT patching |

Despite the name `dynamic-linker.cpp` in `src/dynamic-newlib/`, that implementation
is a *hosted dynamic loader* with revertible GOT patching — it resolves symbols
at load time and records every patch in a journal so `unload()` can restore
pristine state. The "real" dynamic linker — with lazy binding, deferred
resolution, and GOT/PLT indirection — is in `src/dynamic-nolib/`.

**Note:** Both loaders now use a weak `scl_lookup_firmware_symbol` hook for
fallback symbol resolution (libc, C++ runtime, test globals) rather than
hardcoded `strcmp` tables. Applications override this weak default to provide
target-specific symbol mapping. See `REFACTORING_SUMMARY.md` for details.

## 2. Background: GOT, PLT, and Position-Independent Code

### The Problem

A shared object is compiled as position-independent code (PIC). The compiler
doesn't know at compile time where in memory the library will be loaded. Yet the
library needs to access its own global variables and call functions in other
libraries or the main firmware.

### The GOT (Global Offset Table)

The **GOT** is an array of 32-bit pointer slots that lives in the library's
data section. Every reference to a global variable or imported function goes
*through* the GOT:

```
// Instead of reading AA directly:
ldr r0, [pc, #offset_to_AA]   // wrong — AA's address is unknown

// The compiler emits:
ldr r0, [r10, #got_offset]    // r10 holds the GOT base address
                               // reads the *current address* of AA
```

On Cortex-M with `-msingle-pic-base -mpic-register=r10`, the register `r10`
always holds the GOT base address of the **currently executing library**. When
execution enters a library (via a trampoline or PLT), `r10` is set to that
library's GOT base. Every global-variable access becomes `ldr rd, [r10, #N]`.

### The PLT (Procedure Linkage Table)

The **PLT** is a small stub (a few instructions) generated by the linker for
every imported function call. It looks like:

```
func_foo_plt:
    movw ip, #lower(GOT[n])     ; ip = &GOT[n]
    movt ip, #upper(GOT[n])
    ldr  pc, [ip]               ; jump to whatever address is in GOT[n]
```

This is an indirect call through the GOT. The caller doesn't care *where* `foo`
actually lives — it reads the address from the GOT slot and jumps there.

### How the GOT and PLT Interact

```
   caller
     │
     │  bl func_foo_plt
     ▼
   ┌─────────────┐
   │  PLT stub   │  Loads ip = &GOT[n], then ldr pc, [ip]
   └──────┬──────┘
          │
          ▼
   ┌─────────────┐
   │  GOT[n]     │  Contains the *address* of func_foo
   └──────┬──────┘
          │
          ▼
   ┌─────────────┐
   │  func_foo   │  The real function
   └─────────────┘
```

### Why Is a PLT Needed If the Address Is Already in the GOT?

This is one of the most common questions about dynamic linking. If the GOT
already holds the address of every imported function — and the caller could
just read the address and jump — why have a PLT at all?

#### Reason 1: Code cannot be patched; data can

On Cortex-M, the code section (`.text`) typically lives in **flash** — read-only
memory that cannot be modified at runtime. The GOT lives in **RAM** (writable).
The compiler emits `BL func_foo` as a direct branch in the code. If the loader
later needs to change where `func_foo` points (e.g., because a library was
loaded and provides a better implementation, or because lazy binding resolved
the address on first call), it would have to rewrite the `BL` instruction in
flash — **impossible**.

The PLT solves this: the `BL` instruction in the caller's code never changes.
It always branches to a **fixed stub** in the PLT. The PLT stub is a tiny,
position-independent code sequence:

```asm
func_foo_plt:
    movw ip, #lower(GOT[n])      ; 2 instructions to form &GOT[n]
    movt ip, #upper(GOT[n])
    ldr  pc, [ip]                ; 1 instruction to load and jump
```

This never changes. Only the GOT slot changes — and since the GOT is in RAM,
that's trivially writeable.

#### Reason 2: The `BL` instruction has limited range

The ARM `BL` (branch-and-link) instruction encodes a **signed 24-bit offset**
(±32 MB). On Cortex-M, `BL` in Thumb-2 mode has a range of ±16 MB. If the
target function lives in a different library loaded at an arbitrary RAM address,
it may be **millions of bytes away** — far beyond the branch range.

The PLT stub uses `ldr pc, [ip]`, which loads a **full 32-bit address** from
the GOT. This has no range limitation: any function anywhere in the 4 GB address
space can be reached.

#### Reason 3: Lazy binding requires a second indirection

Without a PLT, lazy binding would look like this:

1. The compiler emits `BL func_foo` (a direct branch).
2. On first call, the branch goes to... where? You'd have to point it at a
   resolver trampoline. But `BL func_foo` is baked into the flash image at
   build time — it cannot be changed at runtime.
3. You'd need the loader to patch the flash, which is impossible.

With a PLT, the flow is:

1. The compiler emits `BL func_foo_plt` — a branch to the PLT stub.
2. The PLT stub does `ldr pc, [GOT[n]]`.
3. Before the first call, GOT[n] holds the address of `dl_runtime_resolve`.
4. The resolver patches **GOT[n] only** (in RAM) to the real function address.
5. On subsequent calls, the PLT stub reads the now-correct GOT slot.

The key: **the PLT is the immutable trampoline; the GOT is the mutable data
slot**. The code stays in read-only memory; only the data changes.

#### Reason 4: ARM/Thumb interworking

On ARM, functions can be in ARM mode (4-byte instructions) or Thumb mode
(2-byte/4-byte mixed). Cortex-M is Thumb-only, but the PLT stub still handles
this cleanly: the loaded address from the GOT has the Thumb bit (bit 0) set,
and `ldr pc, [ip]` correctly enters Thumb mode. A direct `BL` to an address
without the Thumb bit would fault (`INVSTATE` exception). The PLT stub
abstracts this: the caller does `BL func_foo_plt` (a relative branch to a
nearby stub), and the stub handles the indirect jump with the correct mode bit.

#### Summary

| Concern | Without PLT | With PLT |
|---|---|---|
| Patching the target at runtime | Must patch flash (impossible) | Patch GOT in RAM |
| Range of call | Limited to ±16–32 MB from the call site | Full 32-bit address space |
| Lazy binding | Impossible (can't change `BL` in flash) | GOT[n] starts as resolver, gets patched on first call |
| ARM/Thumb interworking | Caller must manage mode bit | PLT stub handles it |
| What is the `BL` target? | The real function (unknown until load time) | The PLT stub (known at link time) |


### Reserved GOT Slots

By ARM ELF convention, the first 3 GOT entries are reserved:

| Slot | Name | Purpose |
|---|---|---|
| GOT[0] | — | Address of the `.dynamic` section |
| GOT[1] | — | Link-time identification (not used at runtime) |
| GOT[2] | — | Address of the lazy-resolution trampoline (`dl_runtime_resolve`) |

Data slots start at GOT[3].

## 3. The Two Linker Approaches, Side by Side

| | `src/dynamic-nolib/` (dl.cpp) | `src/dynamic-newlib/` (dynamic-linker.cpp) |
|---|---|---|
| **Execution environment** | Cortex-M bare-metal, freestanding | Host PC, full C++ runtime |
| **Memory model** | Fixed 4-handle pool + arena allocator | Heap (`std::vector`, `std::unique_ptr`) |
| **STL / heap** | None — everything is fixed-size arrays and spans | Full STL — vectors, strings, unique_ptr |
| **Relocation method** | Streaming: reads one `elf::Rel` at a time, patches immediately | Plan-based: reads ALL relocations into a `std::vector<reloc_entry>`, then applies |
| **Symbol resolution** | Per-symbol callback (`symbol_source` function pointer), deferred to the moment it's needed | Bulk: all symbols resolved eagerly in `apply_plan()` |
| **Lazy binding** | Yes — JUMP_SLOTs are patched to `dl_runtime_resolve` after eager pass | No — every slot is resolved eagerly |
| **Lazy mechanism** | PLTn → GOT[n] → `dl_runtime_resolve` → `dl_fixup()` → real target | N/A |
| **Deferred cross-lib resolution** | Optional P6 cross-call: route external JUMP_SLOTs through `dl_cross_call`, resolve at every call, swap r10 | Pending list + cross-resolution pass on each new `dlopen` |
| **Unload revert** | Simple: free the arena (no journal needed) | Full `patch_journal`: every modification is recorded, revert restores original bytes |
| **Patches main firmware** | No — main exports symbols via `link_context`, libraries import them | Yes — `patch_main_got()` writes library-provided addresses into the host's own GOT |
| **Hardcoded symbol table** | None | None — resolves against dynamic symbol table registered via `set_symtab()` at boot |
| **GOT ownership** | Each loaded library has its own GOT; `r10` swapped on library entry | Patches go into the host firmware's existing GOT; no r10 swapping |
| **Cross-lib GOT base** | `r10` is swapped to the callee's `got_base` at call time | Not applicable — all addresses are absolute |
| **Fragment count** | One `.cpp` file (~860 lines) plus 4 port `.c` files | One `.cpp` file (~500 lines) with supporting classes |

## 4. `src/dynamic-nolib/` — True On-Target Dynamic Linker

### Why It Exists

A Cortex-M microcontroller has no MMU, no virtual memory, and typically no heap
allocator (or a very primitive one). Dynamic loading must be deterministic,
allocation-free, and work without any OS services. The `src/dynamic-nolib/` linker
achieves all of that.

### How Loading Works (`dlopen_source`, `dl.cpp:195`)

**Step 1: Parse the ELF header.** `elf_image::parse()` (`elf-image.cpp:26`) reads
the ELF header, validates it's a 32-bit ARM shared object, and stores the header
in memory.

**Step 2: Allocate the image buffer.** `image_arena().alloc()` returns a
contiguous block of RAM large enough for all `PT_LOAD` segments (computed by
`image_size()`, which finds the highest segment end address). The buffer is
zeroed.

**Step 3: Copy PT_LOAD segments.** Each `PT_LOAD` program header is read from
the source (semihosting, flash, etc.) and copied to its virtual-address offset
within the buffer. The buffer is organized as vaddr-addressed memory:
`buffer[0]` corresponds to vaddr `0`, and `buffer[ph.p_vaddr]` is where the
segment lands.

**Step 4: Cache section headers.** `section_cache::load()` (`dl.cpp:89`) reads
the ELF section header table and `.shstrtab` into a fixed-size RAM cache. This
is an optimization: the alternative (calling `elf_image::find_section()`) would
re-read from the semihosting source on every lookup, which is hundreds of
round-trips per `dlopen`. The cache reduces it to exactly 2 reads.

**Step 5: Extract dynamic sections as in-image spans.** The sections
`.dynsym`, `.dynstr`, and `.hash` are allocated (they have the `SHF_ALLOC`
flag), so they already reside in the image buffer. Rather than copying them
again, the code records `std::span`s pointing into the buffer. These spans will
live until `dlclose`.

**Step 6: Build this library's own symbol resolver.** A `symbol_resolver`
(`symbol-resolver.cpp:36`) is constructed over the library's own
`.dynsym`/`.dynstr`/`.hash` triple. This lets the loader look up symbols that
this library *defines* (so other libraries importing from it can find them).

**Step 7: Snapshot the raw GOT.** Before any relocation runs, the current
contents of `.got` are saved to a fixed-size array in the handle (`got_raw[]`).
This is purely for debugging/didactic purposes — `dl_dump_got_walkthrough()`
can show "BEFORE vs AFTER" for every GOT slot.

**Step 8: Eager relocation pass — ALL symbols are resolved and written.**
A `combined_resolver` is created that walks other loaded handles (then main) to
resolve external symbols. Then `reloc_applier::apply_rel()` (`reloc-applier.cpp:15`)
is called for both `.rel.dyn` and `.rel.plt`. This function:

- Reads each `elf::Rel` entry one at a time (streaming, no allocation).
- For **every** relocation type — RELATIVE, GLOB_DAT, JUMP_SLOT, ABS32, REL32,
  COPY — it resolves the symbol name and writes the result into the GOT slot
  (or other target location).
- If the symbol is defined in this image (st_value != 0), computes `base + st_value`.
- If the symbol is external (st_value == 0), calls the `combined_resolver` callback
  to look it up in other loaded libraries or main.
- Unresolved externals are written as 0 (matching `--unresolved-symbols=ignore`).

**After this pass, every GOT slot — including every JUMP_SLOT — holds a valid,
correct, fully-resolved address.** The symbol lookup has happened, the
dependency edges have been recorded (`deps[]` / `refcount`), and everything is
ready to run.

So why go further? Because eager resolution cannot handle mutual imports
(lib A calls lib B, lib B calls lib A — one is always loaded second, and the
first load finds the other missing), and because on Cortex-M (slow semihosting
I/O), deferring function resolution to first call saves load time.

**Step 9: Lazy-binding retrofit — JUMP_SLOTs are UN-resolved.**
Immediately after the eager pass, the code iterates `.rel.dyn` (and `.rel.plt`)
again. Every `R_ARM_JUMP_SLOT` entry has its GOT slot **overwritten** with the
address of `dl_runtime_resolve` (the assembly trampoline in `port/lazy-resolve.c`).

This is deliberately discarding the perfectly good address that was just
computed. The reason: **the eager pass ran to build the dep graph and to ensure
data symbols work; function calls can afford the one-time lazy fixup cost.**

The lazy flow:

1. The PLT stub for `func_foo` loads `ip = &GOT[n]`, then `ldr pc, [ip]`.
2. GOT[n] currently holds `&dl_runtime_resolve` — the lazy trampoline.
3. The trampoline saves all caller registers (r0–r3, d0–d7, lr).
4. It calls `dl_fixup(ip)` (`dl.cpp:465`), which:
   - Finds which handle owns this GOT slot (walks `g_handles` by address range).
   - Re-resolves the symbol name by scanning the relocation tables backwards
     (from GOT offset to symbol index to name).
   - Performs the same resolution as the eager pass (self → other libs → main).
   - Patches `*GOT[n] = real_address | 1` (Thumb bit).
   - Increments `g_fixup_count` (a counter exposed for testing).
5. The trampoline restores all registers and tail-calls the real function.
6. On **subsequent calls**, GOT[n] holds the real address → the PLT stub jumps
   straight there, bypassing the resolver entirely.

**Why waste the eager resolution on JUMP_SLOTs if it's going to be thrown
away?**

1. **Dependency tracking** (`deps[]` / `refcount`): The eager pass distinguishes
   "defined in this library" from "external" for each JUMP_SLOT symbol. This
   drives the dep graph needed for `dlclose()` to refuse unloading a library
   that another loaded library still imports from. Without the eager pass,
   every symbol would look "external" (the lazy trampoline is not the real
   address), and the dep graph would be empty.

2. **P6 cross-call mode**: The cross-call routing (Step 10) needs to know which
   JUMP_SLOTs are self-defined (keep the bound address) vs external (route
   through `dl_cross_call`). The eager pass computes this by checking whether
   `st_value != 0` in the library's own `.dynsym`.

3. **Data symbols are not lazy**: `GLOB_DAT`, `RELATIVE`, `ABS32`, `REL32`, and
   `COPY` keep their eagerly-resolved values. Only `JUMP_SLOT` (function calls)
   is retrofitted for laziness. It would be wasteful to special-case JUMP_SLOT
   in the eager pass when the general streaming reloc applier handles all types
   uniformly.

**Why not skip the eager pass entirely and just resolve lazily from the start?**

Because lazy resolution only works for function calls (JUMP_SLOT). Data
references (`GLOB_DAT` for global variables, `RELATIVE` for vtables/string
pointers, `ABS32` for constructor entries) must be correct from the moment the
library is loaded — constructors run immediately after relocation, and they
dereference globals and vtables directly through the GOT. There is no PLT-style
indirection for data.

**Step 10 (optional): Cross-call routing.** If `g_cross_call` is enabled, every
*external* JUMP_SLOT (one whose symbol is not defined in this library) is
further overwritten with the address of `dl_cross_call` (`port/dl-cross-call.c`).
This trampoline:

- Calls `dl_cross_lookup()` to resolve the symbol at call time.
- Swaps `r10` to the callee's `got_base` for the duration of the call.
- Restores the caller's `r10` on return.

This supports mutual lib↔lib imports (e.g., lib A calls lib B, and lib B calls
lib A) — something that eager-only resolution cannot handle, because one of the
two would not be loaded yet at resolution time.

**Step 11: Constructor execution.** The `.init_array` (or `.inits`) section is
located by section *type* (`SHT_INIT_ARRAY = 14`), not by section *name*,
because the C library's linker script may rename it. Each function pointer is
called through `pic_call_void()`, which is a tiny Thumb trampoline that sets
`r10` to the library's GOT base before calling the constructor and restores it
on return.

**Step 12: Exception-handler registration.** The `.ARM.exidx` range is
registered via `dl_exidx_register()` so the C++ unwinder can find unwind tables
for code executing in this library.

### How Symbol Resolution Works

**combined_resolver** (`dl.cpp:163`): When a relocation needs an external symbol:

1. Scan all 4 handles in `g_handles`. Skip self and unused handles.
2. For each in-use handle, call `handle.resolver.address_of(name)`.
3. If found (non-zero value), record a dependency edge (`h->deps[]`) and return
   `lib.base + st_value`.
4. If no library provides it, fall back to `link_context::resolve()`, which looks
   up main firmware's `.dynsym` (parsed from the `_DYNAMIC` linker array).

**Lazy fixup** (`dl.cpp:465`): At first-call time, `dl_fixup()` repeats the
same resolution order but adds a self-check first:

1. Check if this library itself defines the symbol.
2. Scan other loaded handles.
3. Fall back to main firmware.

**Cross-call lookup** (`dl.cpp:510`): `dl_cross_lookup()` does the same, but
returns both the target address and the callee's `got_base` (packed into a
64-bit value).

### How Unloading Works

`dlclose()` (`dl.cpp:406`):
1. If `refcount > 0`, refuse (another library still imports from this one).
2. Run destructors (`.fini_array`) through `pic_call_void()`.
3. Decrement refcounts on all libraries this one imported from.
4. Unregister the `.ARM.exidx` range.
5. Free the image arena memory.
6. Zero out the handle.

No journal is needed because each library lives in its own isolated arena
buffer — freeing it is sufficient cleanup.

### The `dl.*` API: `dlopen`, `dlsym`, `dlclose`, `dlerror`

The `src/dynamic-nolib/` linker exposes a POSIX-like C API through the `dl` class
(`dl.hpp:87-93`, `dl.cpp:811-857`). Each function is a thin wrapper around the
internal `fw::` functions, with error-string bookkeeping.

#### `dl::dlopen(filename, flags)` (`dl.cpp:811`)

The public wrapper. It delegates to `scl_impl_dlopen()` (`dl.cpp:789`), which
is a **weak symbol** dispatcher that selects the platform-specific loader:

```
scl_impl_dlopen(filename, flags)
  │
  ├─ If g_use_flatfs is set → call fw::dlopen_fs(basename)
  │   (reads library from on-chip flash archive via Flashbyte_source)
  │
  ├─ Else → call fw::dlopen(original path)
  │   (reads library over semihosting)
  │
  └─ If neither weak symbol is defined → error::FILE_NOT_FOUND
```

Both paths eventually call `fw::dlopen_source()` (`dl.cpp:195`), which is the
core loader implementing Steps 1–12 above.

The `flags` parameter (standard POSIX `RTLD_NOW` / `RTLD_LAZY`) is accepted
but **ignored** — the loader always does eager resolution + lazy retrofit
regardless of flag. This is a deliberate simplification: on bare-metal there
is no benefit to deferring the eager pass (data symbols must be resolved
immediately anyway), and the lazy retrofits always happen for function slots.

Returns an opaque `handle*` cast to `void*`.

#### `dl::dlsym(handle, symbol)` (`dl.cpp:825`)

Looks up a symbol by name in a single loaded library's `.dynsym`:

1. Cast the opaque handle back to `fw::handle*`.
2. Call `fw::dlsym(h, name)` (`dl.cpp:400`), which does:
   - `h->resolver.address_of(name)` — a SysV hash lookup in the library's
     own `.dynsym`/`.dynstr`/`.hash` triple.
   - If found, returns `h->base + st_value` (image-relative → absolute).
   - If not found, returns `error::SYMBOL_NOT_FOUND`.
3. The wrapper translates errors to the `dlerror` string buffer.

**Important**: `dlsym` only searches the specified library's symbol table. It
does NOT walk other loaded libraries or main. This matches POSIX semantics
where `dlsym(handle, name)` searches that handle's `DT_SYMTAB` only (unlike
`dlopen`-time resolution which walks all handles).

#### `dl::dlclose(handle)` (`dl.cpp:840`)

Calls `fw::dlclose(h)` (`dl.cpp:406`). See "How Unloading Works" above.

Returns 0 on success. Refuses with -1 if `refcount > 0` (the library is still
imported by another loaded library).

#### `dl::dlerror()` (`dl.cpp:851`)

Returns a human-readable error string for the last failed `dlopen`/`dlsym`/`dlclose`
call. The string is a static buffer; the error is consumed on first read
(conforming to POSIX's "subsequent calls return NULL" contract).

#### Internal helpers (not part of the public API)

| Function | Purpose |
|---|---|
| `dlopen_source(src, rawname)` | Core loader over any `byte_source`: the actual `dlopen` implementation. |
| `fw::dlsym(h, name)` | Single-library symbol lookup. |
| `fw::dlclose(h)` | Unload and free. |
| `dl_enable_cross_call(on)` | Enable/disable P6 cross-call r10 routing (off by default). |
| `dl_cross_trace(level)` | Set GOT/PLT translation trace verbosity for debugging. |
| `dl_dump_image(h)` | Print all GOT/PLT relocation entries with current values and annotations. |
| `dl_dump_main_provides(names, n)` | Print what main provides for a list of symbol names. |
| `dl_dump_got_walkthrough(h)` | Print the full before/after GOT walkthrough with per-slot annotations. |
| `dl_fixup_count()` | Return the number of lazy fixups performed (for test verification). |

### Contrast: `src/dynamic-newlib/` Has No Public `dl.*` API

The `src/dynamic-newlib/` linker is a C++ class (`firmware::dynamic_linker`) with a
different API shape:

| Operation | `src/dynamic-nolib/` (`fw::` / `dl::`) | `src/dynamic-newlib/` (`firmware::dynamic_linker`) |
|---|---|---|
| **Load** | `dl::dlopen(path, flags)` → `handle*` | `linker.load_from_source(src)` → `library*` |
| **Look up symbol** | `dl::dlsym(handle, name)` → `void*` | `linker.lookup(lib, name)` → `void*` |
| **Unload** | `dl::dlclose(handle)` | `linker.unload(lib)` |
| **Last error** | `dl::dlerror()` → `char*` | No equivalent (errors returned via `result`) |

Key difference: `src/dynamic-newlib/`'s `lookup()` searches **four places** (main's
`.dynsym` → hardcoded `addr_of()` table → the library's own `.dynsym` →
cross-library search), while `src/dynamic-nolib/`'s `dlsym()` searches **only** the
given handle's symbol table. The static linker's `lookup()` is a
do-whatever-it-takes resolution function; the dynamic linker's `dlsym()` is a
minimal POSIX-compatible symbol query.

Also, `src/dynamic-newlib/` has no lazy binding, no P6 cross-call, no debugging dump
functions, and no error-string API.

## 5. `src/dynamic-newlib/` — Host-Side Static Patcher

### Why It Exists

Before the on-target dynamic linker was fully mature, this project needed a way
to load and test shared libraries from a host PC environment. The host has a
full C++ runtime, heap, and standard library, so the constraints are completely
different. The name "static" refers to the *resolution strategy* — all names are
resolved at once, like a static linker would do — not to the build-time vs
run-time distinction.

### How Loading Works (`load_from_source`, `static/dynamic-linker.cpp:112`)

**Step 1: Parse the ELF header.** Same `elf_image::parse()` as the dynamic path.

**Step 2: Compute base virtual address.** `image_base()` finds the lowest vaddr
across all PT_LOAD segments. This is the load bias.

**Step 3: Allocate image buffer with journal tail.** `image_memory::load_segments()`
allocates a buffer large enough for the image *plus* extra bytes at the tail for
a `patch_journal`. The journal is placed at the end of the allocation, co-allocated.

**Step 4: Build a relocation plan.** `relocator::compute()` (`relocator.cpp:39`)
reads the entire `.rel.dyn` section (collected by `elf_image::collect_relocations()`)
and builds a `std::vector<reloc_entry>` — one entry per relocation. Each entry
carries:
- The offset to patch.
- The relocation type.
- The symbol name (a `string_view` into the `.dynstr` buffer).
- The symbol value and size.

This is in contrast to the dynamic approach's streaming, which never builds a
plan at all.

**Step 5: Apply the plan.** `apply_plan()` (`static/dynamic-linker.cpp:311`)
iterates the plan and patches each relocation:

- **RELATIVE**: Computes `(base - base_va) + addend`, records the original value
  in the journal, writes the new value.
- **GLOB_DAT / JUMP_SLOT**: Resolves in this order:
  1. If `entry.sym_value != 0`, the symbol is defined in this library: use
     `base + sym_value - base_va`.
  2. Otherwise, try main firmware's `.dynsym` (via `link_context`).
  3. If still not found, try cross-resolution in other loaded libraries
     (`resolve_cross()`).
  4. If still not found, try the hardcoded `addr_of()` table (printf, sinf,
     malloc, etc.).
  5. If *still* not found (sym_addr == 0), record a `pending_reloc` entry so a
     future `dlopen` can re-patch it.
  - Records the original value in the journal, then writes the resolved address.
- **ABS32 / REL32**: Same resolution chain, but adds the in-place addend after
  the symbol address.
- **COPY**: Memcpy from the main firmware's definition into the library's slot.

**Step 6: Patch main firmware's GOT.** `patch_main_got()` (`static/dynamic-linker.cpp:427`)
reads the *host firmware's* `.rel.dyn` section (via `ctx_.reldyn()`). For every
JUMP_SLOT or GLOB_DAT entry whose symbol is defined in the newly loaded library,
it writes the library-provided absolute address into the firmware's GOT slot.
This is how `printf` calls from main can resolve to a library-provided
replacement, or vice versa.

**Step 7: Run constructors.** Same as the dynamic path — iterate `.init_array`
and call each function pointer.

**Step 8: Cross-resolution pass.** After loading the new library, scan all
`pending_reloc` entries. For each one that's still zero, try to resolve it
against the *new* library's `.dynsym`. If found, patch it. Then remove all
resolved entries from the pending list.

### How Symbol Resolution Works

The resolution order is fixed and hardcoded in `apply_plan()`:

1. Self-defined (st_value != 0)
2. Main firmware's `.dynsym`
3. Cross-library (`resolve_cross()` — walks all loaded libs)
4. Main firmware's dynamic symbol table (registered via `set_symtab()` at boot)
5. If all fail → `pending_reloc` (deferred to the next library load)

The firmware's dynamic symbol table is registered using the `set_symtab()` interface at startup, maps well-known names to their respective Flash addresses, and is processed at local memory speeds without hardcoded string parsing.

### How Unloading Works

`unload()` (`static/dynamic-linker.cpp:215`):

1. **Revert the journal**: Every modified byte is restored to its original value
   (pop order, so the last patch written is the first restored). This restores
   the firmware's GOT to its pre-load state.
2. **Prune pending relocs**: Any `pending_reloc` entry whose address falls within
   this library's image buffer is removed (it would be a dangling pointer
   otherwise).
3. **Erase the library**: Remove the `unique_ptr` from the `libs_` vector, which
   frees the image memory.

The journal-based revert is essential here because patches go directly into
the *host firmware's own memory* (its GOT, its data sections), not into an
isolated arena. Without the journal, unloading would leave corrupted state.

### The `dynamic_linker` Class API

The `src/dynamic-newlib/` linker is a C++ class (`include/dynamic-newlib/dynamic-linker.hpp:40-96`)
constructed with a reference to the host firmware's `link_context`:

```cpp
dynamic_linker linker(link_context());
```

#### `load_from_source(src)` — Load library

Takes a `byte_source` (same interface as the dynamic path). Returns a `library*`
on success, or an `Error`. Internally it:

1. Parses the ELF.
2. Allocates image memory + journal tail (co-allocated).
3. Builds a relocation plan (std::vector).
4. Applies the plan (resolves all symbols eagerly, journals every write).
5. Patches main firmware's GOT (`patch_main_got`).
6. Runs constructors.
7. Attempts cross-resolution for pending relocs from previous loads.
8. Appends the library to the internal `libs_` vector.

All errors are returned through `result<library*>` — there is no
error-string-based API like `dlerror`.

#### `unload(lib)` — Unload library

Takes the `library*` returned by `load_from_source`. Reverts the journal,
prunes pending relocs that point into this library's memory, and removes it
from the `libs_` vector. The `unique_ptr` destructor frees the image buffer.

#### `lookup(lib, name)` — Resolve Symbol Name to Address

Searches in this order (see source `static/dynamic-linker.cpp:234-281`):

1. **Main firmware's `.dynsym`** — the host firmware's exported symbol table
   (via `link_context::dynsym()` / `dynstr()` / `hash()`).
2. **Main firmware's dynamic symbol table** — registered via `set_symtab()` at boot (and loaded via Flash/Semihosting).
3. **The specified library's own `.dynsym`** — using the in-image spans that
   were recorded at load time.
4. **Cross-library search** (`resolve_cross()`) — walks every library in
   `libs_` (except the one being looked up) and searches each one's `.dynsym`.

This is a **do-whatever-it-takes** resolution that searches broadly. It is
used internally during `load_from_source` (in `apply_plan`) and is also
available to test code that needs to look up symbols across the entire loaded
library set.

#### No Pending-Error API

Unlike `dl::dlerror()`, the static linker does not accumulate a last-error
string. Every failure is returned immediately through the `result` type.

#### Contrast Summary

| Aspect | `src/dynamic-nolib/` | `src/dynamic-newlib/` |
|---|---|---|
| **API style** | POSIX-like C functions (`dl::dlopen`, etc.) | C++ class methods |
| **Load** | `dlopen(path, flags)` | `linker.load_from_source(src)` |
| **Symbol query** | `dlsym(handle, name)` — one library only | `lookup(lib, name)` — searches main + registered symtab + lib + cross |
| **Unload** | `dlclose(handle)` | `linker.unload(lib)` |
| **Error reporting** | `dlerror()` returns last error string | Errors via `result<T>` return values |
| **Error string on fail** | `dlopen` returns `nullptr`, string via `dlerror` | `load_from_source` returns `Error` directly |
| **Debug/dump** | `dl_dump_image()`, `dl_dump_got_walkthrough()`, etc. | None |
| **Lazy binding** | Yes (two-pass: eager then lazy retrofit) | No (all eager) |
| **Lazy fixup counter** | `dl_fixup_count()` for test proof | N/A |
| **Cross-call routing** | Optional P6 mode (`dl_enable_cross_call`) | N/A |
| **Hardcoded symbols** | None | None (uses registered symbol table) |

## 6. How the GOT Is Used in Each Approach

### `src/dynamic-nolib/` — Per-library GOT, r10-Swapped

Each loaded library has its **own GOT** embedded in its image buffer. The GOT
starts at the `.got` section's vaddr within the image. The `got_base` is
recorded in the handle:

```
handle.got_base = base + got_offset
```

When entering a library function (via a constructor call, PLT stub, or
`dlsym`), `r10` is set to that library's `got_base`. This is done by the
`pic_call_*` trampolines in `port/pic-trampoline.c`:

```asm
push {r10, lr}
mov  r10, r1        ; r1 = got_base argument
blx  r0             ; call the function
pop  {r10, pc}
```

The library's compiled code accesses globals via `ldr rd, [r10, #N]`, so
changing `r10` effectively switches to that library's global data.

**GOT layout per library:**

```
                 ┌──────────────┐
  GOT[0]         │ .dynamic addr │
  GOT[1]         │ (reserved)    │
  GOT[2]         │ dl_runtime_   │  ← points to lazy resolver trampoline
                 │   resolve     │
  GOT[3]         │ data sym 0    │  ← holds absolute address of variable
  GOT[4]         │ data sym 1    │
  ...            │ ...           │
  GOT[N]         │ func sym M    │  ← JUMP_SLOT: initially resolver, then real fn
                 └──────────────┘
```

GOT[2] is special: the lazy-binding trampoline `dl_runtime_resolve` uses the
PLT stub's `ip` register (which points to `&GOT[n]`) to identify which slot
triggered the fixup. It does not use GOT[2] itself (the approach deliberately
bypasses the linker's PLT0, whose GOT-relative offset arithmetic is unreliable
on Cortex-M).

**What happens during a cross-library call (P6 mode):**

```
lib_a calls lib_b_func()

  bl  lib_b_func_plt        ; PLT stub in lib_a
    └─ movw/movt ip, &GOT[n]  ; ip = address of lib_a's GOT[n]
       ldr pc, [ip]            ; GOT[n] holds &dl_cross_call

dl_cross_call trampoline:
  push {r4-r7, r10, lr}      ; save caller's r10
  bl   dl_cross_lookup(ip)   ; resolve: which lib defines this symbol?
    └─ returns {target|1, callee_got}
  mov  r10, callee_got        ; SWAP r10 to the callee's GOT base
  blx  target                 ; call the real function (with callee's globals)
  pop  {r4-r7, r10, pc}       ; restore caller's r10, return
```

### `src/dynamic-newlib/` — Single Shared GOT, Direct Patching

There is **one** GOT — the host firmware's `.got`/`.got.plt`. When a library is
loaded, its symbols' absolute addresses are written directly into the firmware's
existing GOT slots. There is no per-library GOT, no r10 swapping, and no
indirection through a trampoline.

```
Host firmware's GOT (single, shared):

  GOT[0]   .dynamic addr
  GOT[1]   (reserved)
  GOT[2]   dl_runtime_resolve (if lazy mode; usually not used)

  GOT[3]   printf     ← address of host's printf()
  GOT[4]   sinf       ← address of host's sinf()
  ...
  GOT[N]   lib_func   ← written by patch_main_got() to point into the loaded library
```

When `patch_main_got()` runs, it iterates the host's `.rel.dyn` and writes the
loaded library's absolute function addresses into the host's GOT slots. After
that, any code in the host that calls `lib_func()` via the PLT will jump
directly to the library's code.

There is no mechanism to swap context — the library must be compiled
compatibly with the host's PIC model, or the addresses are adjusted
appropriately.

## 7. Step-by-Step: Loading a library

### `src/dynamic-nolib/` (on target)

```
dlopen("libfoo.so")
  │
  ├─ 1. Parse ELF header (validate ET_DYN, ARM, 32-bit)
  ├─ 2. Compute image size, allocate from arena
  ├─ 3. Copy PT_LOAD segments into arena (vaddr-addressed)
  ├─ 4. Cache section headers (2 reads: SHT + .shstrtab)
  ├─ 5. Extract .dynsym / .dynstr / .hash as in-image spans
  ├─ 6. Build this library's symbol_resolver
  ├─ 7. Snapshot raw GOT (for debug)
  ├─ 8. EAGER PASS: stream .rel.dyn, .rel.plt through reloc_applier
  │     For each entry: read elf::Rel, look up symbol via combined_resolver,
  │                     patch the slot directly. No plan stored.
  ├─ 9. LAZY PASS: overwrite every JUMP_SLOT GOT slot with
  │     &dl_runtime_resolve (or &dl_cross_call if cross-call mode)
  ├─10. Run constructors through pic_call_void (sets r10 to this lib's got_base)
  ├─11. Register .ARM.exidx for C++ unwinding
  └─12. Return handle
```

**On first call to a lazy-bound function:**
```
PLTn → GOT[n] = &dl_runtime_resolve → save args → dl_fixup(&GOT[n])
  → resolve symbol → patch GOT[n] = real_address → restore args → bx real_address
```

### `src/dynamic-newlib/` (on host)

```
dynamic_linker::load_from_source("libfoo.so")
  │
  ├─ 1. Parse ELF header
  ├─ 2. Compute base_va, allocate image + journal tail
  ├─ 3. Copy PT_LOAD segments
  ├─ 4. Read .dynsym, .dynstr, .hash sections
  ├─ 5. BUILD RELOCATION PLAN: read ALL .rel entries into std::vector<reloc_entry>
  ├─ 6. APPLY PLAN: for each entry:
  │     │   Resolve: self → main .dynsym → cross-lib → addr_of() → pending_reloc
  │     │   Journal original value
  │     │   Patch the slot
  │     └─ (JUMP_SLOTs are resolved eagerly, NOT left for lazy binding)
  ├─ 7. PATCH MAIN GOT: iterate host's .rel.dyn, write lib addresses into host's GOT
  ├─ 8. Run constructors (direct call, no r10 trampoline needed)
  ├─ 9. CROSS-RESOLUTION PASS: scan pending list, patch entries now resolvable
  └─10. Return library*
```

### Why the Host-Unit Tests Are Called "dynamic1–5" Despite Testing Common Code

Historical naming: the common core was originally developed alongside the
`src/dynamic-nolib/` loader, so the host unit-test suites were prefixed "dynamic".
They primarily validate the shared core, not the `src/dynamic-nolib/` pipeline.
The `test-dynamic-nolib/` on-target tests exercise the actual `src/dynamic-nolib/`
pipeline end-to-end on hardware.

### Vendored `dl-impl.cpp` vs `src/dynamic-nolib/dl.cpp`: Two Independent `dl::` Facades

Both `test-dynamic-newlib/` and `test-dynamic-nolib/` call the same `dl::dlopen` / `dl::dlsym`
/ `dl::dlclose` / `dl::dlerror` API. But they get that API from **different
files** that are **independent implementations** sharing only the function
signatures.

| Aspect | `src/dynamic-nolib/dl.cpp` | Vendored `dl-impl.cpp` |
|---|---|---|
| **Full path** | `src/dynamic-nolib/dl.cpp` | `test/platforms/.../vendor/firmware/src/dl-impl.cpp` |
| **Backend** | Uses `fw::dlopen_source()` — the allocation-free, two-pass (eager+lazy), arena-based dynamic loader | Uses `firmware::dynamic_linker` — the heap-allocated, plan-based, journaled static patcher from `src/dynamic-newlib/` |
| **handle type** | `fw::handle*` (from `include/dynamic-nolib/dl.hpp`) — has `got_base`, `lazy`/`lazy_plt` tables, `exidx_base`, fixed-size `got_raw[]` snapshot | `firmware::library*` (from `include/dynamic-newlib/dynamic-linker.hpp`) — has `image_memory`, `patch_journal`, `base_va`, VA/size metadata |
| **handle storage** | Fixed pool of 4 in `.bss` (`g_handles[4]`) | `std::vector<std::unique_ptr<library>>` in the `dynamic_linker` singleton |
| **dlsym behaviour** | Searches the **specified handle's `.dynsym` only** (`h->resolver.address_of(name)`). No cross-lib, no main fallback. | Calls `g_linker.lookup(h, name)` which searches **4 places**: main `.dynsym` → registered `symtab` table → library's own → cross-library |
| **dlclose** | Frees the arena buffer, decrements refcounts, unregisters exidx. | Calls `g_linker.unload()` which reverts the patch_journal, prunes pending relocs, frees heap memory. |
| **dlerror** | Static char buffer with POSIX consume-on-read | Static `const char*` pointer, same pattern |
| **Error strings** | Returns descriptive strings like `"Not an ELF file"`, `"Short read"` | Returns short codes like `"NotElf"`, `"ShortRead"` |
| **Code location** | Part of the SCL itself (`scl-dynamic` library) | Vendored copy in the platform's firmware tree under `vendor/` |
| **Used by** | `test-dynamic-nolib/test1/2/3` (and any app linking `scl::dynamic-nolib`) | `test-dynamic-newlib/test1/2` (and the original `static-unify-code` project) |

**Why does the vendored copy exist?**

The `src/dynamic-newlib/` loader was originally developed in a separate project called
`static-unify-code`. When it was integrated into the SCL, the portable core
went into `src/` and `include/`, the loader class went into `src/dynamic-newlib/`, and
the test firmware (with its platform-specific `dlopen` front-end) was left as a
**vendored copy** under the board platform directory
(`test/platforms/board-hosted/vendor/`). This avoided reworking the
test infrastructure to use `src/dynamic-nolib/dl.cpp`'s internal API.

The two `dl::` facades serve the same purpose — provide `dlopen`/`dlsym`/`dlclose`
to application code — but are **completely independent implementations** wired
to different loader backends.

## 9. How Complete Is the ELF32 Parser?

**Short answer: not a complete ELF32 parser.** It covers only the subset
needed to load ARM shared objects into an embedded Cortex-M system, and
explicitly rejects everything else. The design is minimal-by-necessity: the
parser runs on bare-metal with no heap, no file I/O library, and extremely
limited RAM.

### What It Parses

| ELF component | What the parser does |
|---|---|
| **ELF header (`Ehdr`)** | Validates magic (`0x7fELF`), class (32-bit), endianness (LE), machine (ARM), type (shared object). Reads all fields into an in-memory struct. |
| **Program headers (`Phdr`)** | Reads individual `PT_LOAD` entries on demand to compute image size/footprint and to copy segments into the arena. Non-`PT_LOAD` program headers are skipped silently. |
| **Section headers (`Shdr`)** | Reads individual section headers on demand via `section_header(index)`. `find_section(name)` scans all sections to locate `.dynsym`, `.dynstr`, `.hash`, `.rel.dyn`, `.rel.plt`, `.got`, `.init_array`, `.fini_array`, `.ARM.exidx` by name. |
| **Symbol table (`.dynsym`)** | Treated as an array of `elf::Sym` (16 bytes each). Individual entries are read via `load_word` into the 3 fields needed: `st_name`, `st_value`, `st_size`, `st_info`. |
| **String table (`.dynstr`)** | Random-access NUL-terminated string lookups via `name_at()` (a bounds-checked `strnlen` equivalent). |
| **Hash table (`.hash`)** | Implements the classic SysV ELF hash algorithm: `nbucket` / `nchain` / bucket array / chain array. Walks the chain until a match or chain end. |
| **Dynamic section (`_DYNAMIC`)** | Parses the `DT_NULL`-terminated array of `Dyn` entries to extract `DT_HASH`, `DT_SYMTAB`, `DT_STRTAB`, `DT_STRSZ`. |
| **Relocation entries (`Rel`)** | Reads raw 8-byte entries (the ARM REL format — no `r_addend`). Classifies 6 types via `r_type()`, extracts the symbol index via `r_sym()`. |

### What It Does NOT Parse (Deliberately)

| ELF feature | Status | Why excluded |
|---|---|---|
| **RELA relocations** | Not supported | ARM uses `REL` format (addend is in-place in the image word, not in `r_addend`). RELA (used by x86-64, AArch64) has no addend-in-place and would give wrong results. |
| **GNU hash (`.gnu.hash` / `DT_GNU_HASH`)** | Not supported | Only SysV `.hash` is parsed. Libraries built with `--hash-style=gnu` or `both` are rejected (symbol lookup silently fails). All project `.so` files use `--hash-style=sysv`. |
| **`.init` / `.fini` sections (old-style)** | Not supported | Only `.init_array` / `.fini_array` (section type `SHT_INIT_ARRAY` = 14, `SHT_FINI_ARRAY` = 15) are recognized. The old `SHT_PROGBITS` `.init` section with a single function pointer is not. |
| **`.preinit_array`** | Not supported | The dynamic linker spec defines a pre-initialization array; this loader ignores it. |
| **TLS (thread-local storage)** | Not supported | No `R_ARM_TLS_*` relocation types are handled. Cortex-M bare-metal has no thread-local storage model. |
| **Debug sections (`.debug_*`, `.stab*`)** | Ignored | The parser skips non-`SHF_ALLOC` sections by default. Debug info is never read. |
| **NOTE segments / sections** | Ignored | `PT_NOTE` program headers and `SHT_NOTE` sections are skipped. |
| **`.ARM.attributes`** | Ignored | The section exists in the test fixtures but is never read. ABI-flag validation (soft vs hard float) is not done at the ELF level — the test scripts (`verify-test-libs.sh`) check this out of band. |
| **`.comment` / `.note.gnu*`** | Ignored | Toolchain metadata is never parsed. |
| **`SHT_DYNAMIC`** | Only `_DYNAMIC` | The dynamic section is read via the `_DYNAMIC` linker symbol in the *firmware*, not from the loaded library. The loaded library's `.dynamic` is not parsed — the loader instead reads `.dynsym`/`.dynstr`/`.hash` sections directly by name. |
| **`PT_DYNAMIC`** | Not used | The program-header-based dynamic segment is not read. |
| **`PT_GNU_EH_FRAME`** | Not used | The GCC EH frame header is not needed — exception handling uses EHABI (`PT_ARM_EXIDX`). |
| **`PT_GNU_STACK`** | Not used | Stack executability is irrelevant on bare-metal. |
| **`PT_GNU_RELRO`** | Not enforced | The relro segment is present in the test .so files but the loader does not mprotect pages (no MMU). |
| **`.interp` section** | Ignored | Not relevant — there is no dynamic linker to invoke. |
| **`.gnu.version` / `.gnu.version_r`** | Ignored | Versioning information is not checked. |
| **Symbol visibility (`.dynsym` `st_other`)** | Ignored | `STV_HIDDEN`, `STV_PROTECTED`, `STV_DEFAULT` are all treated identically. |
| **`R_ARM_GOT32`, `R_ARM_PLT32`, etc.** | Not supported | These are linker-emitted relocations used during the link step, not at load time. The loader only handles the 6 runtime relocation types. |
| **`R_ARM_THM_*` relocations** | Not supported | The compiler/linker resolves Thumb-specific relocations at build time; they should not appear in the final `.so`. |
| **64-bit ELF (ELFCLASS64)** | Explicitly rejected | The parser requires `EI_CLASS == 1` (32-bit). |
| **Big-endian (ELFDATA2MSB)** | Explicitly rejected | The parser requires `EI_DATA == 1` (little-endian). |
| **Non-ARM architectures** | Explicitly rejected | `e_machine` must be `40` (ARM). |
| **Relocatable objects (ET_REL)** | Explicitly rejected | `e_type` must be `3` (shared object). Executables (ET_EXEC) and core files (ET_CORE) are also rejected. |

### Relocation Types: What's Handled vs What's Missing

**Handled** (the 6 ARM runtime relocations that appear in a fully-linked `.so`):

| Type | Value | Used for |
|---|---|---|
| `R_ARM_RELATIVE` | 23 | Base-relative fixups (string pointers, vtable, constructor pointers) |
| `R_ARM_GLOB_DAT` | 21 | GOT entries for imported global variables |
| `R_ARM_JUMP_SLOT` | 22 | GOT entries for imported functions (PLT slots) |
| `R_ARM_ABS32` | 2 | Absolute 32-bit data references (constructor entries, static data) |
| `R_ARM_REL32` | 3 | PC-relative 32-bit references (EHABI typeinfo in `extab`) |
| `R_ARM_COPY` | 20 | Copy relocation for extern variables defined in main |

**Not handled** (would cause `error::UNSUPPORTED_RELOC`):

- `R_ARM_GOT32` (link-time GOT formation)
- `R_ARM_PLT32` (link-time PLT formation)
- `R_ARM_GOTOFF` (link-time GOT-relative addressing)
- `R_ARM_GOTPC` (link-time GOT base computation)
- `R_ARM_THM_CALL`, `R_ARM_THM_MOVW_ABS_NC`, `R_ARM_THM_MOVT_ABS`, etc.
- `R_ARM_TLS_DTPMOD32`, `R_ARM_TLS_DTPOFF32`, `R_ARM_TLS_TPOFF32`
- `R_ARM_NONE`
- `R_ARM_V4BX`
- All other ARM relocation types (the ARM ELF ABI defines ~130 types)

The missing types are **link-time relocations** — they are resolved by the
linker when building the `.so` file and should never appear in the final
shared object's `.rel.dyn` / `.rel.plt` sections. If one does appear (e.g.,
from a misconfigured build), the loader rejects it cleanly.

### Design Philosophy

This is not a general-purpose ELF tool like `readelf` or `libelf`. It is a
**minimal loader core** with three priorities:

1. **Freestanding**: Compiles for Cortex-M bare-metal with no libc, no heap,
   no file I/O.
2. **Deterministic**: Fixed memory pools, no `std::vector`, no unbounded
   allocation.
3. **Fail-fast**: Every unsupported feature produces a clear error return
   (`error::UNSUPPORTED_RELOC`, `error::BAD_SECTION`, `error::NOT_SHARED_OBJECT`)
   instead of silently producing wrong results.

The parser validates the ELF header just enough to confirm it can handle the
file, then reads only the bytes it needs — individual program headers,
section headers by index, and relocation entries one at a time. It never
loads the entire ELF structure into memory.

## 10. Why Two Approaches?

### Historical / Development Context

The `src/dynamic-newlib/` approach came first. It was written to run on a host PC for
rapid prototyping and testing, where heap allocation and STL containers are
available. The name "dynamic_linker" reflects that it loads `.so` files — which
are "dynamic" objects — even though the resolution strategy is static.

The `src/dynamic-nolib/` approach was implemented later when the project needed to
run *on the actual Cortex-M target*, where heap allocation is unavailable or
prohibitively expensive, and where lazy binding and position-independent code
with r10-based GOT access are necessary for correctness.

### Fundamental Design Differences

**Why `src/dynamic-nolib/` uses lazy binding:**
- Reduces load time: only fix up the functions that actually get called.
- Supports mutual imports: if lib A and lib B call each other, lazy binding
  (or cross-call routing) resolves at call time, after both are loaded.
- The P6 cross-call mechanism is an extension of this: it resolves on *every*
  call and swaps r10, enabling full isolation between library GOTs.

**Why `src/dynamic-newlib/` uses eager resolution with a journal:**
- Simpler to debug: all symbols are resolved immediately; no lazy surprises.
- The journal is needed because the host firmware is a single process — patches
  go into its own memory space and must be revertible. The dynamic approach
  avoids this entirely by isolating each library in its own arena.
- The symbol table (`set_symtab`) is used to dynamically pass the host
  firmware's symbol table to the loader at boot, avoiding any hardcoded symbol mappings.

**Why `src/dynamic-nolib/` doesn't need a journal:**
- Each library is loaded into its own arena allocation. On `dlclose`, the entire
  arena is freed. Nothing outside the arena is modified.
- Main firmware's GOT is never touched — main already has its own exports
  resolved by the linker at build time. Libraries import *from* main, not the
  other way around.

**Why `src/dynamic-newlib/` patches main's GOT:**
- The host test environment may not have a proper pre-linked firmware with a
  complete `.dynsym`. library functions that override or extend main's symbols
  must be visible to main's PLT entries. `patch_main_got()` makes that happen
  by writing directly into the host's GOT slots.

### Summary Analogy

Think of `src/dynamic-nolib/` as a proper **shared library loader** like Linux's
`ld.so` — each `.so` gets its own GOT, symbols are resolved on demand, and
indirection through the PLT is the normal calling convention.

Think of `src/dynamic-newlib/` as a **runtime linker** that behaves more like a
static linker running late: it reads all relocations, resolves every name
immediately, and writes final addresses directly into the running program's
memory — then keeps a journal so it can undo those writes on unload.

### The Naming Inversion

By Linux convention, "dynamic linker" means lazy binding, deferred resolution,
per-library GOT/PLT, and `dlopen`/`dlsym`/`dlclose`. "Static linker" means
all-at-once resolution, no indirection, no deferred binding.

In this project, the names are **inverted**:

| Directory | Does at runtime | Memory | Resolution | Naming convention |
|---|---|---|---|---|
| `src/dynamic-nolib/` | **Less** — fixed pools, no heap, no journal, minimal | Static/allocation-free | Per-symbol, can be lazy | Should be called "static" |
| `src/dynamic-newlib/` | **More** — heap allocation, plan building, cross-resolution passes, journaling, patching main GOT | Dynamic/heap-heavy | All-at-once, eager | Should be called "dynamic" |

If you renamed them according to their Linux convention:

- `src/dynamic-nolib/` → `src/ldso/` or `src/rtld/` (the actual runtime linker)
- `src/dynamic-newlib/` → `src/loader/` or `src/patcher/` (the eager batch resolver)

But the historical naming stuck: `src/dynamic-newlib/` was written first (in the
`static-unify-code` project) and processes `.so` files = "dynamic objects" at
runtime, hence "dynamic_linker". `src/dynamic-nolib/` came later and got the name
that was still free, even though it is behaviorally more "static" in its
resource usage.

## 11. Suggestions for Improvement

These recommendations follow from the analysis above, ordered by impact.

### 1. Rename `src/dynamic-newlib/` to match what it does

`src/dynamic-newlib/dynamic-linker.cpp` containing class `dynamic_linker` is actively
misleading to anyone familiar with ELF loading conventions.

**Suggested rename:**
- `src/dynamic-newlib/` → `src/loader/`
- `dynamic_linker` class → `Loader` or `BatchPatcher`
- `include/dynamic-newlib/dynamic-linker.hpp` → `include/loader/loader.hpp`
- CMake target `scl::dynamic-newlib` → `scl::loader`

This would make the directory tree self-documenting: `src/dynamic-nolib/` = dynamic
linker, `src/loader/` = batch loader/patcher.

### 2. Unify the two `dl::` facades into one

`src/dynamic-nolib/dl.cpp` and the vendored `dl-impl.cpp` both expose the same
`dl::dlopen`/`dlsym`/`dlclose`/`dlerror` API, but with **different semantics**
for `dlsym` (one searches only the given handle, the other searches everything
via `lookup()`). This is a latent bug: someone writing test code against one
backend and running it against the other will get different results.

**Options:**
- **(A)** Make `scl::dynamic-newlib` also use `src/dynamic-nolib/dl.cpp` by adding a backend
  abstraction (e.g., a `LoaderBackend` interface with two implementations:
  `ArenaLoader` and `HeapLoader`). Then `dl::dlsym` has identical behaviour
  regardless of which backend is linked.
- **(B)** Delete the vendored `dl-impl.cpp`. Have `test-dynamic-newlib/` compile
  `src/dynamic-nolib/dl.cpp` but inject the `scl::dynamic-newlib` backend through the
  abstraction from (A). The `dl::` API lives in exactly one place.
- **(C)** Failing that, at minimum add a comment to both `dlsym` implementations
  warning that their search scope differs.

### 3. Eliminate the vendored `vendor/` tree

`test/platforms/board-hosted/vendor/` is a frozen copy of the old
`static-unify-code` project. It:
- Duplicates SCL functionality (its own `.so` fixture build recipes,
  `dl-impl.cpp`, test sources).
- Has its own build system (`Makefile_DYN`/`Makefile_NO_DYN`) with its own
  compiler flag decisions.
- Drifts from the SCL over time (different fixture `.so` builds, different
  test coverage).

**Options:**
- **(A)** Migrate the vendored test sources into `test-dynamic/test-dynamic-newlib/` proper.
  Move `dl-impl.cpp` into `src/` (or eliminate it per suggestion 2). Build
  the `.so` fixtures through CMake instead of sub-makes.
- **(B)** Replace the vendored tree with a git submodule pointing to the
  original `static-unify-code` repository at a tagged commit.

### 4. Add `DT_NEEDED` auto-loading to `src/dynamic-nolib/`

Currently the caller must `dlopen` dependencies in the correct order. The
`.dynamic` section of each `.so` contains `DT_NEEDED` entries listing its
dependencies. Parsing them and recursively loading dependencies (with cycle
detection) would make the loader self-sufficient.

**Challenge:** The fixed 4-handle pool (`g_handles[4]`) would need to grow,
become dynamic, or be backed by a larger compile-time constant. The recursion
depth is bounded by the dependency graph, not by the number of libraries the
user loads directly.

### 5. Add GNU hash (`DT_GNU_HASH`) support to `symbol_resolver`

Modern ARM toolchains emit `.gnu.hash` by default (`--hash-style=gnu` or
`both`). The current `symbol_resolver` (`src/symbol-resolver.cpp:36`) uses
only the legacy SysV `.hash` section. A library built without `--hash-style=sysv`
will silently fail (`SymbolNotFound`) on every lookup — a hard-to-diagnose bug.

**Implementation sketch:** Add an alternative lookup path in
`symbol_resolver::address_of()`. Detect the `.gnu.hash` section by checking
for `DT_GNU_HASH` in the `_DYNAMIC` array (or by section name). The GNU hash
format uses Bloom filters for fast rejection and a different chain layout.
Both hash tables can coexist — try gnu hash first (faster), fall back to SysV.

**Test:** Add a CI build that links the test `.so` fixtures with
`-Wl,--hash-style=both` to exercise both paths.

### 6. Replace the hardcoded `addr_of()` table with runtime `.dynsym` parsing (Completed)

We completely replaced the hardcoded fallback tables with an embedded, build-time generated `.scl_symtab` dynamic symbol table parsed using a host-compiled C++20 helper tool (`gen-symtab.cpp`). The table is registered at startup using `set_symtab()` and resolved dynamically, keeping both loaders generic and robust.

### 7. Add `.init`/`.fini` legacy section support

Some embedded toolchains emit old-style `.init`/`.fini` sections — a single
function pointer in a `SHT_PROGBITS` section — instead of the newer
`.init_array`/`.fini_array` in `SHT_INIT_ARRAY` sections. The current code
(`dl.cpp:383`) finds constructors **only** by section type (`kShtInitArray`),
missing `.init` entirely.

**Fix:** After the type-based lookup fails, add a name-based fallback for
`.init` and `.fini`.

### 8. Add compile-time relocation-type coverage check

An unknown relocation type is currently a runtime error
(`error::UNSUPPORTED_RELOC`). In a debug build, the loader could catch missing
types at compile time with:

```cpp
template <std::uint8_t...> struct RelocSet {};
using HandledTypes = RelocSet<2, 3, 20, 21, 22, 23>;
// static_assert that classify() covers all elements of HandledTypes
```

Or more practically, a `switch` with GCC/Clang `-Wswitch` already catches
missing `enum class` values — the `classify()` function in `relocator.cpp`
should use a switch instead of an if-else chain.

### 9. Document the single-threaded assumption explicitly

The code uses module-level globals (`g_handles`, `g_sc`, `g_fixup_count`)
without any locking. This is correct for bare-metal Cortex-M single-threaded
firmware, but a reader from the Linux world (where `dlopen` must be
thread-safe) will assume a bug.

**Fix:** Add a comment at the top of `dl.cpp`, `dynamic-linker.hpp`, and
`symbol-resolver.hpp`:

```cpp
// Thread-safety: not required. This runs on bare-metal Cortex-M with a
// single thread. The fixed-size handle pool and arena are not re-entrant.
```

### 10. Add CI for `--hash-style=both`

The test `.so` fixtures are built with SysV hash (`--hash-style=sysv`).
Nothing in CI builds them with `--hash-style=gnu` or `--hash-style=both`,
so a regression in SysV hash parsing or a missing GNU hash path would go
unnoticed until someone links a real library with default toolchain flags.

**Fix:** Add a CI step (or a CMake option) that rebuilds the fixtures with
`-Wl,--hash-style=both` and runs the dynamic1–5 host-unit tests against
them. If suggestion 5 (GNU hash support) is implemented, this CI step
proves it works.

## 12. A third model — eager ET_REL loading (`scl::reloc`)

The two loaders above both consume **ET_DYN** objects (`-fPIC -shared`) with a
GOT/PLT. There is a third, fundamentally different way to load code, added as
`scl::reloc`: load **ET_REL** objects — plain relocatable `.o`s built
`-mlong-calls -fno-pic -r`, the way the **Linux kernel loads a module**.

### The one difference that matters: **when** a cross-reference is resolved

When module A calls `b_fn` in module B:

| | ET_DYN (GOT/PLT) — `scl::dynamic-nolib` | ET_REL (`-fno-pic`) — `scl::reloc` |
|---|---|---|
| the call compiles to | `ldr pc,[GOT slot]` (indirect) | `ldr rN,=b_fn ; blx rN` (absolute literal) |
| at load, the slot/literal holds | a resolver stub (GOT) | it **must already be `b_fn`'s real address** |
| target address is known | **lazily**, at the first call (`dl_cross_call`/`dl_fixup`) | **eagerly**, at load time |
| load order / cycles | don't matter (indirection decouples them) | **must see the whole group at once** |
| per-call cost afterwards | one GOT indirection, forever | a direct call (faster, smaller) |
| needs `r10`/trampoline, PLT0/GOT[2] | yes | **no — none of it** |

The GOT is an *indirection* that decouples "a reference exists" from "its target
is known", which is exactly what makes lazy binding and cyclic loading trivial.
`-fno-pic` removes that indirection: the address is baked into the code, so it
must be known when the module is placed.

### Why cyclic modules force `load_set`

The demo fixtures are mutually dependent: `c1 → c2`, `c2 → c1` **and** `c2 → cpp3`,
`cpp3 → c2`. You cannot load `c2` alone — its references to `c1_into_fm`/`cpp3_step`
have nowhere to point yet. So `reloc::load_set` does it in **two phases over the
whole group**: (1) *place* every module (now every symbol has an address), then
(2) *resolve* every relocation (any module can now see any other's symbols), then
run all `.init_array`. That is precisely what a static linker — or the kernel's
module loader over a dependency group — does. It is the **eager** analogue of the
ET_DYN loaders' lazy `dl_cross_call`.

### The payoff, measured

The `test-relocatable/` battery loads `relprov+relmod` and the cyclic `c1+c2+cpp3` set
via `load_set`, calls into them, and gets values **bit-identical** to the ET_DYN
`dyn2` battery: `c1_call_c2(5) = 17467`, `c1_use_fm() = 611`, `cpp3_recurse(6) =
21`, `cpp3_method(2,100) = 1432`. Same behaviour, no GOT/PLT/r10 anywhere — and
the *main firmware* collapses from a `-pie` image with `.dynsym`/GOT/`_DYNAMIC`
(~150 KB) to an ordinary `ET_EXEC` (~10 KB) with a ~40-line linker script (see
[build-linking-guide.md](build-linking-guide.md) §3.5). The trade-off in one line: **GOT/PLT** pays one
indirection per call forever for trivial lazy/cyclic loading; **ET_REL** pays a
heavier "know the whole set at load" link for direct, indirection-free calls.

### The naming, completed

`scl::dynamic-nolib` / `scl::dynamic-newlib` / `scl::static` are all **ET_DYN +
GOT/PLT** flavours. `scl::reloc` is the **ET_REL, no-GOT** flavour — the other
half of the design space. See its loader in `src/reloc/`, the fixtures in
`test-relocatable/fixtures-reloc/`, and the run recipe in [build-and-test.md](build-and-test.md).

## 13. Drawbacks of ET_REL (`-r`) vs ET_DYN (`-shared`)

§12 explains *why* eager ET_REL loading works. This section is the honest cost
side — what you give up choosing `-r` (`scl::reloc`) over `-shared` (the GOT/PLT
loaders), roughly in order of how much it bites on a microcontroller.

### 13.1. Code must live in writable RAM — no execute-in-place
`-r -fno-pic` patches the actual instructions (ABS32 literals, `THM_CALL`
encodings) *inside* `.text`, so every byte of code must be copied into RW RAM and
modified. A module's `.text` **cannot stay in flash and run XIP**. A `-fPIC`
`.so` never self-modifies code — only its small **GOT** (a few hundred bytes) is
patched in RAM, so its `.text` can execute from flash. On a RAM-poor part loading
a large module, this is the single biggest drawback.

### 13.2. Eager, whole-set loading — no lazy binding
Every relocation must resolve at load time; one missing symbol fails the whole
load. So the host must supply **all** imports up front, and **cyclic modules
cannot be loaded one at a time** — they force `load_set` (place-all-then-resolve).
ET_DYN's lazy `dl_cross_call`/GOT indirection makes load order and cycles a
non-issue, and lets you "load a lib, pay only for what you call."

### 13.3. Not position-independent — re-relocate per load address
The module is bound to one absolute arena address. Loading it elsewhere requires
re-running the entire relocation pass; you cannot share one loaded copy, map it
read-only, or relocate-once-run-many. A PIC `.so` loads anywhere with just `+base`.

### 13.4. `-mlong-calls` undercuts the "direct calls" advantage
To reach flash↔RAM (>±16 MB) without a GOT, `-r` needs `-mlong-calls`, which turns
**every** call into `ldr rN,=target ; blx rN` — a literal-pool load + register
branch — even for near calls. So ET_REL trades the GOT's one indirection for a
literal indirection at every call site, plus larger code. It is GOT-free, but not
a plain `BL`.

### 13.5. Heavier, trickier relocation processing
ET_REL carries the full compiler relocation set against `.symtab`, and the loader
must patch **instruction encodings** (the Thumb-2 `BL` split-immediate is fiddly;
the Thumb bit for `STT_FUNC` and the `.init_array` addend are easy to get subtly
wrong). ET_DYN's dynamic relocs are a compact, uniform set
(`RELATIVE/GLOB_DAT/JUMP_SLOT/ABS32/COPY`) — all simple 32-bit word writes into the
GOT/data, no encoding surgery. More relocations, more load-time work.

### 13.6. Slower / larger symbol handling
Lookup is a **linear scan of `.symtab`** (no `.hash`), and ET_REL retains the full
symbol table (locals + section symbols) — more metadata to ship and parse.
ET_DYN's `.dynsym` + SysV `.hash` gives O(1) lookup and exposes only exported/
imported names.

### 13.7. No dynamic-linking semantics or metadata
No `DT_NEEDED` (the host must know the module set — no auto-loading of
dependencies), no clean **symbol interposition / weak-override** model, no
standard "loadable object" contract. It is a partial-link intermediate needing a
custom loader (the kernel-module model), not a portable shared object.

### 13.8. Where `-r` still wins
- No `r10` PIC-base register reserved → better register allocation for DSP/math.
- The **main firmware is far simpler** — an ordinary `ET_EXEC`, no `-pie`/
  `.dynsym`/GOT/`_DYNAMIC` (~10 KB here vs ~150 KB for the ET_DYN main).
- GOT-free data access; no cross-call trampoline complexity; standard static
  toolchain (no dynamic linker scripts).

### 13.9. Rule of thumb

| Situation | Prefer |
|---|---|
| Many/large modules, flash-heavy & RAM-poor MCU | **`-shared`** (code stays in flash, lazy binding) |
| Occasional small self-contained plugins, RAM to spare | **`-r`** (lean main, no GOT) |
| Need lazy/partial loading, interposition, `DT_NEEDED` | **`-shared`** |
| Need register-max codegen, simplest possible main | **`-r`** |

That is why this repo keeps **both**: `-shared` buys flash-resident code, lazy
binding, position independence and real dynamic-linking semantics at the cost of a
GOT indirection and a heavier main; `-r` buys a trivially simple main and no GOT
at the cost of code-in-RAM, eager whole-set loading, per-load re-relocation, and
instruction-encoding relocation complexity.
